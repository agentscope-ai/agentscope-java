# 显式新 Turn 的短事务受理

[English](new-turn-admission.en.md)

仅优化事件批次中每一项都是显式 `user.message` / `new_turn`、且没有 `turn_id` 的请求。普通消息、取消、注入、steer、interrupt、混合事件批次以及执行恢复保持原有协调路径。不改变接口或持久化格式，不增加 Schema、Topic 或消费组。

## 流程

原路径先锁 Session，再读取策略、校验输入、访问限速器、查询应用额度和序列化 Turn，最后登记协议回执。外部调用或统计变慢会让同一 Session 的其他操作一起等待。

新路径分成两段：

1. 锁外先查询已提交的幂等回执。已有请求直接返回原回执；摘要不一致返回冲突。API 的认证和授权仍在这一步之前执行。
2. 新请求在锁外运行策略/输入校验，准备稳定的 Turn 身份及规范化输入，执行宽松应用额度与限速检查。纯校验与条件策略同步可能在并发同键请求中重复执行；它们不承担执行副作用的去重。
3. 进入短事务取得 Session 行锁，再次查询幂等回执。其他请求可能已经在预检期间提交；此时返回它的原回执，不再次追加。
4. 锁内重新检查 Session 生命周期、checkpoint 管理占用、子 Agent 准入资格及 Session 排队容量，原子分配序号，保存 Turn、公开事件与请求回执。明确新 Turn 不要求 Session 空闲，继续自动排队。批次中的任何一项失败，整个登记事务回滚。
5. 提交后沿用原有 MQ 发布与持久 outbox 恢复流程。预检先后不承诺为 HTTP 到达顺序；序号由实际登记决定，执行顺序仍由既有发布/FIFO 协议保证。

如果业务预检拒绝请求，会在一个短锁定事务中再查原回执：并发同键请求刚刚成功提交时，原回执优先于过期的预检拒绝；确实没有提交记录时才返回原错误。数据库访问故障直接传播，由客户端保留原幂等键重试。

## 边界

Session 锁仍用于原子状态修改，没有贯穿推理或工具等待。锁内保留必要的数据库写入及协议投影，并非无锁受理。应用级额度可能在预检和登记之间变化，沿用宽松额度语义；Session 生命周期与本地队列容量则在锁内重新判断。

取消、注入、恢复等依赖当前目标或执行状态的逻辑不使用预检快速路径，包含这些操作的混合批次整体保持原协调方式。单独的旧 Turn 提交/恢复内部接口也保持原调用方式。

## 回归

真实 PostgreSQL 验证暂停输入校验或限速检查时，同 Session 的注入仍能完成；当前 Turn 保持执行，新 Turn 排队。另验证预检期间关闭 Session 后拒绝追加、并发不同键产生唯一序号、同键重放、同键不同内容冲突、并发容量校验、批次失败整体回滚，以及并发成功回执优先于过期拒绝。对普通消息、取消、注入和混合批次使用实际行锁超时探针确认原协调方式仍在。
