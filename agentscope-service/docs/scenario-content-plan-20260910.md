# AgentScope Service 场景案例设计

本文记录 2026-09-10 调整后的案例方向，是教程与示例工程的开发方案，不是端到端执行报告。原来的小函数修复、固定 webhook 和知识摘要保留为局部能力练习；官网主案例以以下三个完整业务流程展开。

## 1. Hosted Team：从 GitHub Issue 到可合并 PR

### 业务目标与固定需求

准备一个独立 Java 示例仓库，包含订单查询接口、固定测试数据、测试命令和 CI。GitHub Issue 提出“订单列表增加状态筛选与分页”，附接口预期、边界情况和验收标准。最终交付可追踪到原 Issue 的 PR、测试结果、Review 记录和审批结论。

全部执行角色使用 Hosted Agent，包括 Leader。Provider 可先统一使用一个已验证的实现，后续再展示不同 provider 混用；角色划分不依赖原生 Subagent。

| 角色 | 职责 | 必须交付 |
| --- | --- | --- |
| Leader / 需求分析 | 读取 Issue 和仓库约束，澄清需求，委派和协调返工 | 验收清单、任务拆分、最终交付索引 |
| Developer | 定位代码、实现功能、补充测试、提交分支并创建 PR | 提交、PR、变更说明和本地测试证据 |
| Reviewer | 检查实际 diff、边界条件、实现质量与测试覆盖 | 针对具体提交的 Review、待修项或认可结论 |
| QA | 独立复现、核对 CI、分析失败并验证修复 | 测试报告、CI run 与对应提交标识 |

### 完整协作过程

1. 将 GitHub Issue 引入 Service 工作，保留外部对象身份并指派 Team。
2. Leader 读取需求、验收条件和仓库说明；缺少关键输入时记录问题并等待补充。
3. Developer 在任务自己的 checkout 中创建功能分支，实现、运行测试并提交 PR。
4. Reviewer 与 QA 获取 PR 的明确提交版本，分别检查代码和测试。成员不依赖共享可写目录传递代码。
5. 将 Review 意见和 CI 失败证据交给 Developer；Leader 明确安排返工任务，不能把一条评论等同于已启动后续执行。
6. 更新 PR 后，针对新的 head commit 重新检查 Review 与必需 CI；保留历史证据，但不能将旧提交通过的结果当作新提交的结果。
7. 使用独立审查身份并按仓库规则完成 GitHub Approve；记录是否仍需项目管理员批准或合并。Service 的工具批准、Issue 验收与 GitHub PR Approve 分别展示。
8. 默认终点为满足约定验收条件的可合并 PR；如案例启用合并步骤，显式配置执行角色与仓库权限，合并后再核对 Issue 状态。

### 集成与失败分支

- GitHub Work Source 负责外部工作的关联与同步；PR、Review、CI 操作通过 Hosted 的 GitHub CLI、MCP 或专用工具完成，逐项验证。
- 首版通过明确任务查询 CI 结果完成闭环；事件驱动变体再增加 CI 事件接收、关联原 PR/工作和去重，不能把通用 webhook 收到事件等同于自动恢复原 Team。
- 验证需求不清、CI 失败、Review 要求修改、Host 断线、推送冲突以及更新提交后证据失效。
- 不在开发本教程时操作用户真实仓库的 Issue、PR 或审批；真实演示执行使用专门授权的样例仓库。

## 2. External Team：企业订单履约异常处理

### 业务价值

客服或运营提交订单号和“客户要求明天到货”等诉求。团队跨订单、库存、物流和售后系统查证，给出可执行方案，并在允许的规则与审批范围内执行、核对结果。目标是减少跨系统人工查询和转派，让每项建议、动作和失败都有证据。

Agent 使用 AgentScope Java 开发，分别注册为 External Agent；各应用有自己的工具、系统连接和部署生命周期。Leader 也由 AgentScope 应用实现，并提供协调、委派和完成节点的能力。

| Agent 应用 | 封装的业务能力 | 返回结果 |
| --- | --- | --- |
| 履约协调 Agent | 识别异常与客户目标，组织调查和动作 | 处置方案、执行顺序、最终结果 |
| 订单 Agent | 查询订单、交付承诺和订单状态 | 订单事实、可执行动作及限制 |
| 库存 Agent | 查询多仓可用库存和调拨条件 | 可选仓库、数量和约束 |
| 物流 Agent | 查询运输节点与时效信息 | 当前进度、异常证据和可选路径 |
| 售后 Agent | 查询服务政策，创建跟进或变更请求 | 政策依据、处理单和操作结果 |

### 典型任务

“订单 O-1001 迟迟未发货，客户希望明天收到，请查明原因并给出处理方案。”

协调 Agent 按证据判断是库存不足、仓库未出库还是承运异常，按需调用成员，而不是每次无条件执行全部角色。示例数据固定展示：原仓缺货、另一仓有货但有调拨限制，客户诉求仍需结合时效决定，不能凭模型推断保证到货。

流程为：业务应用提交 Endpoint Job → SSE 展示调查进展 → Team 汇总事实与方案 → 必要审批 → 执行业务动作 → 再查询业务系统核对结果 → 返回处理单与客户答复。

涉及正式业务审批时，使用显式工作记录或 Workflow approval 关口衔接执行；不能依靠 Endpoint Job 自动完成状态替代业务授权。Agent 调用失败或审批被拒绝时保留已确认事实，给出转人工原因。

### 示例工程与验收

- 提供可本地启动的模拟 OMS、WMS、TMS 和售后接口，具有状态与失败注入；不是把预设模型回复当作集成结果。
- 模拟系统中提供正常订单、缺货、物流异常、数据不一致和业务接口不可用等用例。
- Agent 业务工具使用明确输入输出，写操作带业务幂等标识；验证重试不会重复创建处理单。
- 先验证每个 External 应用的任务接入、隔离、取消与结果回传，再验证完整 Team。
- 验收包括事实来源、动作条件、处理单身份、操作后状态、重复请求和失败转人工。
- 生产替换章节解释如何把模拟接口换成真实企业系统，保留同一业务契约和验收数据。

## 3. Managed Team：从客户需求到售前方案与 PoC 计划

### 业务目标

用户在控制台创建托管 Agent，绑定公司产品资料、能力矩阵、交付规范和案例知识，提交客户需求后交付可审阅的售前方案。基础版本全部使用 Managed Agent，无需先开发或部署 Agent 应用。

固定输入为一份虚构连锁零售企业的客服系统需求，包含业务量、现有渠道、数据边界和期望交付时间；其中有意缺少部分信息，用于验证团队主动列出待确认事项。

| 角色 | 绑定资料与职责 | 交付 |
| --- | --- | --- |
| 方案负责人 | 交付规范；分工、追问、汇总 | 一份完整方案和交付索引 |
| 需求分析 Agent | 需求模板；分析诉求与约束 | 需求清单、优先级和澄清问题 |
| 产品方案 Agent | 产品手册、能力矩阵和案例 | 需求到能力的映射、建议架构和限制 |
| 交付规划 Agent | 项目模板、依赖与验收规范 | PoC 范围、里程碑和验收方法 |
| 质量复核 Agent | 事实依据与交付规范 | 来源核对、矛盾、遗漏与不支持的承诺 |

### 基础教程

1. 准备固定需求文档和知识资料，明确文档路径、版本和来源。
2. 在控制台逐个创建 Managed Agent，配置指令、模型、Environment 和必要的 Memory 绑定。
3. 单独测试各角色，再组建 Team；提交需求与输出要求。
4. 团队输出 Markdown 方案、需求映射表、PoC 计划、待确认问题与来源索引，并交付 Artifact。
5. 在 Inbox 核对事实、下载文件、要求修改并显式安排后续执行，再验收结果。
6. 修改一条产品能力资料，使用新任务验证方案更新和版本追溯。

### 混合编排扩展

- 加入 External 能力查询 Agent，从企业系统读取当前产品可用区域或实施资源；动态事实由接口返回。
- 加入 Hosted PoC Agent，基于通过评审的方案生成演示工程并运行测试；通过提交或 Artifact 交付给 Managed 团队。
- 先完成纯 Managed 路径，再逐项增加外部连接。只有使用带认证的 MCP 等连接时才讲 Vault，不把所有资源强行放入最小示例。

验收包括关键结论可追溯、产品不支持的能力没有被承诺、缺失输入被列出、交付文件可读、评审反馈可追踪。

## 内容编写与实施顺序

三个案例都拆成“业务目标与架构、准备、角色与工具、搭建、跑通主流程、失败与返工、验收与清理”章节，附完整样例资料或工程。功能参考页链接到对应的业务步骤。

先完成研发案例的可运行仓库与 GitHub 交互，再完成企业订单的 AgentScope 应用和模拟业务接口，最后完成 Managed 知识包与纯托管路径、补充混合扩展。现有小练习放入相关主案例的基础练习部分，避免继续作为三个主要业务场景。

文档与验证区分：代码审查确认的能力、在本地模拟系统验证的行为、需要真实 GitHub/provider/模型执行的行为。没有执行证据时只记录验收方法，不把设计流程写成已验证结果。
