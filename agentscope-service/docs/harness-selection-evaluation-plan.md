# Managed Agents Harness 评测目标与选型调研

日期：2026-11-02。[English](harness-selection-evaluation-plan.en.md) · 第二篇：[评测实施方案](harness-selection-evaluation-implementation.md)

本篇面向产品、架构和选型评审，分为两个独立的评测部分。第一部分回答 **Harness 能否把问题处理好**；第二部分回答 **Managed Agents 能否把执行过程可靠地托管起来**。两部分分别定义目标、场景、方法和交付结论，最后共同支持选型。部署拓扑、测试组件、发起命令、评分计算和故障处理统一见第二篇。

| 评测部分 | 评测对象与核心问题 | 主要产出 |
| --- | --- | --- |
| 第一部分：Harness 效果与能力 | 在明确的模型、工具和环境条件下，Harness 如何理解、规划、调用工具并完成任务 | 分场景能力画像、任务质量、重复表现、能力增益与任务消耗 |
| 第二部分：Managed Agents 平台要求 | 承载各候选 Harness 的完整服务链路，能否保证持续执行、多租户隔离和副作用正确性 | 托管准入结论、可靠性与容量证据、平台或适配缺陷、运维维护成本 |

**选型同时需要“能力适合”和“平台要求达标”。** 高任务分不能抵消权限或副作用问题；平台验收通过也不能证明某个 Harness 更善于解决问题。首轮正式候选为 AgentScope Java、Pi、Codex Rust，最终可以选择统一默认内核，也可以按业务场景为新 Session 选择不同内核。

## 第一部分：Harness 处理问题的效果与能力

### 1.1 目标与达成方式

本部分只回答一个问题：**在模型、任务、工具和资源预算可比的条件下，不同 Harness 能把问题处理得多好，其推理与执行机制带来了什么差异。** 评测对象包括任务规划、工具使用、上下文管理、反馈纠错、Skills 运用和协作机制。模型与外部工具也会影响结果，因此结论限定于已验证的实验配置。

| 需要回答的问题 | 达成方式 | 形成的能力证据 |
| --- | --- | --- |
| 相同模型和工具下，哪种 Harness 更能完成任务 | 在共同条件下运行结果可核验的任务，按任务类型配对比较 | 任务成功率、结果质量及推理/执行错误类型 |
| 各自的上下文、Skills、子 Agent 等机制是否有效 | 设置原生能力赛道，并做有/无机制的配对实验 | 单项机制增益、适用条件及额外调用消耗 |
| 随着问题复杂度提高，Harness 的能力边界在哪里 | 按任务难度、步骤长度、工具数量和上下文长度分层比较 | 性能退化趋势、常见失效点和能力边界 |
| 完成任务的效果是否稳定、代价是否合理 | 同题重复运行，同时记录质量、模型/工具消耗和任务耗时 | 重复成功表现、成功任务成本及质量与消耗的取舍 |

应用领域为能力实验提供任务载体。评测重点是同一问题如何被不同 Harness 处理，以及差异来自哪些机制。公开榜单提供任务和方法参考，能力结论来自受控实验及可追溯的逐题证据。

### 1.2 需要覆盖的能力维度

| 能力维度 | 用于观察能力的任务 | 判断重点 |
| --- | --- | --- |
| 规划与任务分解 | 多步骤、跨工具、存在依赖和中间目标的任务 | 能否形成有效步骤、保持目标，并根据中间结果调整计划 |
| 工具选择与调用 | 大工具集、复杂 schema、连续调用、工具返回错误 | 能否选对工具、构造正确参数、利用结果并修正调用 |
| 上下文与记忆利用 | 多轮澄清、长历史、上下文压缩、事实更新和跨会话问答 | 能否保留关键信息、处理冲突、正确检索并在证据不足时停止猜测 |
| 执行反馈与自我纠错 | 命令失败、测试失败、无效搜索、部分完成的任务 | 能否诊断错误、改变策略并最终解决问题 |
| Skills 与协作 | 有/无 Skills、单 Agent/子 Agent 分工的配对任务 | 机制是否带来可重复的质量增益，额外调用是否值得 |
| 指令与约束遵循 | 多重规则、输出要求、不可信工具内容与提示注入 | 能否识别有效指令、遵循约束并保持任务目标 |
| 结果质量与完成效率 | 可核验答案、代码、分析结果和文档产物 | 结果是否正确、完整、可用，成功需要多少步骤、调用和时间 |

各基准映射到以上维度。浏览器/桌面任务观察感知与动作决策，多 Agent 任务观察分工与信息整合，办公任务观察复杂产物生成。只有被测配置具备对应接口且评分可复现时，才纳入相应比较；未测项明确标注。

### 1.3 Harness 候选与能力比较范围

本轮候选为 **AgentScope、Pi、Codex**，三者作为同等被测对象。**每个纳入本轮评测的场景都安排三种 Harness 对比，使用同一批任务和统一评分标准。** 评测范围按任务场景与能力维度确定，不依据候选的产品定位或已有印象分配不同考题，也不预设任何候选在某项能力上的优势。

| 比较项目 | 三种 Harness 统一遵循的要求 |
| --- | --- |
| 场景与任务覆盖 | 覆盖第 1.4 节本轮实际启用的全部场景；同一场景使用相同任务清单、难度分层和重复次数 |
| 能力评价维度 | 均按第 1.2 节评价规划、工具使用、上下文与记忆、反馈纠错、Skills 与协作、指令遵循、结果质量及效率 |
| 实验条件 | 在同一赛道内固定模型、任务指令、环境初始状态、资源与调用预算；共同工具条件及允许的原生机制差异按第 1.6 节预先声明 |
| 评分与结果报告 | 使用相同版本的官方评分器或固定 rubric，统一统计口径；同时展示逐题结果、重复表现、任务消耗和可评分覆盖 |
| 机制差异验证 | 对实际可用的上下文、Skills、子 Agent 等机制做有/无配对实验；依据证据解释增益，不把功能清单直接当作能力结论 |

缺少某项原生机制，不等于退出整个任务场景；能通过共同工具完成任务的候选仍然参测。确实缺少任务必需接口时，明确记录“不支持”或“未评测”及原因，保留在覆盖矩阵中；在共同可评分任务上比较效果，并单列各自覆盖缺口，不通过选择性删题改善成绩。

分别记录三个候选的版本、模型、提示配置、工具集合及实际启用的机制。新增候选或变体沿用相同任务范围和公平性约定；需要检验特定机制时另设对照实验。名称、实现语言和功能清单本身不作为能力得分，具体优势由评测结果确定。

### 1.4 数据集选择与取舍

业界没有覆盖全部 Agent 能力的单一权威榜单。选集依据是：能否观察 Harness 机制差异、任务难度是否有区分度、官方评分是否可核验、环境是否可复位，以及结果是否便于与已有研究比较。每类保留主要代表，以有限任务覆盖不同的能力维度。

**优先级含义：P0 建立核心能力基线；P1 补充长任务与机制对照；P2 扩展到需要专门接口或评分条件的能力实验。** 新基准均先跑通环境与评分器，再冻结题目、版本和预算。下表中的版本不能自动跟随上游 `main` 升级。

| 能力类别 | 选定基准及优先级 | 选择依据 | 对应的任务能力 |
| --- | --- | --- | --- |
| 多工具规划与执行 | **[AppWorld](https://github.com/StonyBrookNLP/appworld)，P0** | 多步规划、工具发现与跨应用状态修改集中在同一可控环境，适合观察完整工具执行链 | 检验任务分解、工具组合、执行顺序与最终状态正确性。 |
| 多轮交互与约束遵循 | **[τ-bench 家族](https://taubench.com/)：原版 τ-bench 为 P0，τ²-bench 为 P1** | 同时包含用户沟通、明确规则与工具调用，可观察多轮决策的重复表现 | 检验澄清策略、目标保持、约束遵循及同题重复成功率。 |
| 通用助手与跨工具推理 | **[GAIA](https://huggingface.co/datasets/gaia-benchmark/GAIA)，P0** | 组合搜索、文件理解与工具使用，提供多种问题求解路径 | 检验搜索、文件和推理的组合能力；按模态说明范围，避免把文本成绩推广到完整多模态能力。 |
| MCP 与函数调用 | **[MCPMark](https://github.com/eval-sys/mcpmark)，P0；[BFCL V4](https://gorilla.cs.berkeley.edu/leaderboard.html)，P1 诊断** | MCPMark 检查真实环境状态变化；BFCL 帮助定位工具选择、参数和多轮协议问题 | 检验工具选择、参数构造、调用衔接和结果利用，以最终状态及协议诊断辅助归因。 |
| 终端与系统任务 | **[Terminal-Bench](https://www.tbench.ai/)，P0** | 对文件、Shell、错误修复和长执行链路有直接区分度，也是三种内核的重要共同工作面 | 检验命令规划、执行反馈利用、错误定位和连续修复能力。 |
| 软件工程 | **[SWE-Bench Pro V2](https://labs.scale.com/leaderboard/swe_bench_pro_public_v2?tab=full)，P1** | 覆盖真实仓库修改；采用网络限制与干净环境重评分，有利于控制取巧和测试污染 | 检验仓库理解、修改定位、补丁生成与测试反馈驱动的修复能力。 |
| 搜索与研究 | **[BrowseComp-Plus](https://texttron.github.io/BrowseComp-Plus/)、[DeepResearch Bench II](https://agentresearchlab.com/benchmarks/deepresearch-bench-ii/)，P1** | 前者固定检索语料，适合隔离 Harness 与搜索引擎差异；后者补充完整研究报告的信息、分析及表达质量 | 固定语料帮助隔离检索器差异，完整报告检验证据收集、综合分析与可交付性。 |
| 浏览器与桌面 | **[WebArena-Verified](https://servicenow.github.io/webarena-verified/latest/)，P2；[OSWorld 2.0](https://osworld-v2.xlang.ai/)，P2** | 前者适合可复位网站工作流；后者覆盖长时间跨桌面应用任务 | 检验界面理解、动作选择、执行反馈与长链路目标保持；需具备对应图像/动作接口。 |
| 长历史与长期记忆 | **[LongMemEval](https://github.com/xiaowu0162/LongMemEval)，P1** | 检查信息更新、跨会话检索、时间关系和无法回答时的行为，补足短任务缺口 | 检验长历史中的事实保留、更新、检索与冲突消解是否正确。 |
| Skills 与扩展机制 | **[SkillsBench v1.1](https://www.skillsbench.ai/)，P1** | 同题有/无 Skills 成对比较，直接量化 Harness 扩展机制的净收益 | 检验 Harness 发现、选择和运用 Skills 的效果，以及额外调用是否值得。 |
| 数据分析与办公产物 | **[DABstep](https://arxiv.org/abs/2506.23719)、[GDPval 公开 gold 子集](https://openai.com/index/gdpval/)，P2** | 前者以多步分析和可核验答案为主；后者衡量实际文档、表格等交付物 | 检验分析步骤、计算正确性、结果验证与交付物质量。 |
| 多 Agent 协作 | **[MultiAgentBench / MARBLE](https://arxiv.org/abs/2503.01935)，P2** | 可观察协作拓扑、任务完成及里程碑收益 | 检验委派是否提高任务完成质量、信息整合效果，以及额外调用消耗是否值得。 |
| 安全与提示注入 | **[AgentDojo](https://agentdojo.spylab.ai/)，P0** | 在工具返回中引入不可信指令，可观察任务执行过程中的指令判断 | 检验指令来源辨别与任务目标保持，同时观察任务效用和攻击成功率。 |

AppWorld 重点观察跨工具规划和状态修改，MCPMark 重点观察 MCP 工具使用和执行结果；GAIA 观察综合问题求解，BrowseComp-Plus 观察固定检索条件下的搜索策略。它们有重叠，因此按能力维度解释结果，不按任务总量累加。

SWE-bench Verified 保留为历史对照；编码主评测使用固定版本及明确的污染控制条件。科研训练、完整论文复现、移动端和攻防竞赛本轮不单列：这些方向需要额外实验条件，先完成现有能力维度的对照，再根据尚未解释的能力差异决定是否增加。

#### 为什么采用这组组合

优先选择能把任务成败与规划、上下文、工具使用或纠错行为联系起来的基准。状态检查、测试和明确答案提供直接结果证据；报告和办公产物使用固定 rubric 与人工抽检。

- **先建立规划与交互基线。** AppWorld 与 τ-bench 同时包含多步骤工具操作和规则约束，适合比较执行策略与多轮决策。
- **补齐工具与执行方式。** GAIA、Terminal-Bench 与 MCPMark 分别观察综合求解、终端操作和 MCP 工具使用。
- **直接检验 Harness 机制。** 长历史、Skills 和协作实验通过配对条件量化各机制的效果。
- **观察指令判断。** AgentDojo 检验不可信内容对任务决策和完成效果的影响。
- **减少重复覆盖。** 同类只保留主要代表，按能力维度汇总，避免题量较大的基准掩盖其他能力。

公开基准暴露具体失效模式后，可补充小规模机制诊断题：例如增加工具数量、延长无关历史、改变错误反馈或设置相互冲突的信息。每组只改变一个因素，用于解释失败原因，诊断结果与官方基准成绩分开报告。

### 1.5 评测框架选择

被测 Harness 负责推理、规划和工具决策；外部评测框架负责提供任务、控制实验条件、采集轨迹和判定结果。评测框架不得代替 Harness 完成被测能力。

| 层次 | 选定实现 | 能力评测中的用途 |
| --- | --- | --- |
| 任务组织与结果归档 | **现有 `general-agent-eval` Runner** | 复用任务执行、多轮用户模拟、重复实验、轨迹采集与官方评分链路 |
| 容器任务与 verifier | **[Harbor](https://docs.harborframework.com/)** | 复用 Terminal-Bench 等任务的环境与评分封装，保持被测 Harness 承担规划和执行决策 |
| 数据集与 scorer 复用 | **[Inspect AI](https://inspect.aisi.org.uk/agents.html)，按需** | 通过外部 Agent 接口复用适合的数据集、评分器和实验日志 |

Harbor 在这里指评测框架。框架选择关注任务与评分复用、实验可重复性，以及是否完整保留被测 Harness 的决策过程。接入框架后仍需逐项确认基准版本、工具条件和评分口径；运行与接入步骤见[实施方案](harness-selection-evaluation-implementation.md)。

### 1.6 如何比较效果与形成能力结论

本节把三个目标落实为可复核的分析过程：**先取得逐题官方成绩，再在相同条件下比较能力；通过机制开关实验解释增益；最后把质量变化与任务消耗放在一起判断。** 三种 Harness 使用相同流程，不能只凭功能特点、单次成功案例或一个汇总分得出结论。

#### 1.6.1 先固定比较条件

| 能力赛道 | 固定条件 | 允许差异 | 能回答的问题 |
| --- | --- | --- | --- |
| **A 共同工具与短上下文** | 同模型、任务指令、工具 schema/结果格式、输入长度、调用预算及计算资源 | 各自推理循环、必要原生协议提示、可逆工具名称映射 | 基础规划、工具使用和执行循环的效果差异 |
| **B 原生上下文策略** | 同模型、长任务、初始输入、外部工具及总预算 | 原生压缩/裁剪、摘要及历史保留；辅助模型调用也计入预算 | 长任务下上下文机制的收益与损失 |
| **C 原生能力组合** | 同任务、模型及总预算；明确各自工具与机制清单 | Skills、文件/Shell、子 Agent、工具发现等实际可用能力 | 机制组合后的任务表现、能力边界及额外消耗 |

B 检验上下文策略，C 比较实际启用的能力组合。工具范围或接口不同的配置单独报告；多项条件同时变化的成绩差不能解释成某一个机制的收益。三种候选在同一赛道使用相同任务、难度分层和重复次数，固定资源、并发及调度规则，保留全部尝试；开发集用于调试，独立决策集用于形成正式结论。

#### 1.6.2 结论一：哪种 Harness 在哪些能力维度更强

**第一步，给每次任务执行评分。** 以最终答案、产物、测试结果或环境状态为依据，不用“Agent 声称完成”代替结果检查。

| 结果类型 | 如何取得成绩 | 如何汇总 |
| --- | --- | --- |
| 官方成功/失败判定，如任务状态检查、完整测试通过 | 按固定版本官方规则记录成功为 1、失败为 0 | 先计算同题多次执行的平均成功率，再按任务/模板组汇总；保留基准原有官方汇总指标 |
| 连续分或产物质量，如研究报告、办公交付物 | 使用官方评分器或预先冻结的 rubric，固定裁判版本与提示，隐藏候选身份并抽检争议结果 | 保留原始量纲及分项分；同题重复后比较均分，自定义评分不得标成官方成绩 |
| 多指标结果，如提示注入下的任务效用与攻击成功率 | 分别计算各项官方指标，明确越高越好或越低越好 | 并列报告，不把攻击成功率、任务成功率和里程碑分直接相加 |

官方分与执行状态分别记录。对二值任务，同时报告：**端到端成功率 = 官方成功次数 / 全部已尝试次数；可评分成功率 = 官方成功次数 / 有有效官方评分的次数；评分覆盖率 = 有有效官方评分的次数 / 全部已尝试次数。** 尚未运行项另列。执行或评分异常不伪造为官方 0 分；有效的官方失败必须保留。重复稳定性另报“同题预定重复次数均成功的任务比例”，披露完整评分题与全部计划题两个分母，不挑最好一次作为任务成绩。

**第二步，形成按能力维度组织的成绩矩阵。** 测试前冻结“任务/基准 → 能力维度”的映射及主要指标；每个维度展示三种候选在相同任务和预算下的成绩、难度分层、重复表现与覆盖率。一个基准可能同时涉及规划、工具和上下文，因此高任务分首先证明该类任务表现更好；要归因为某项具体机制，还需下一节的对照证据。默认保留各基准原始分；如需综合分，预先固定归一化与权重，同一任务不能因多个能力标签被重复计入。

**第三步，判断差异是否足以支持结论。** 在相同题目上计算候选间的题均分差或成功率差（百分点），按独立任务/模板组进行配对重采样，给出差值及 95% 置信区间；重复执行、Turn 和工具调用不充当新增独立题。多候选比较的校正方法和“最小有意义差异”在实验前约定。只有按指标优劣方向计算的区间下界超过该差异，且样本覆盖可信时，才形成“在该维度、配置和预算下更强”的结论；否则报告“有提升趋势”或“证据不足”，不把未发现差异写成能力相同。

共同可评分题用于配对比较，同时展示全部尝试的失败与缺失分布。若缺失集中于某候选或某类难题，不据此宣布排名；先分析缺失对结论的影响，必要时修复后在新的完整匹配批次复核。

#### 1.6.3 结论二：差异与哪些机制有关

在**同一 Harness、同一批任务、同模型与预算**下，只改变一个预定机制，例如开启/关闭上下文压缩、提供/不提供同一组 Skills、启用/禁用子 Agent。其余条件保持一致，并核验机制是否实际触发；无法独立开关或伴随其他配置变化时，记录为组合实验。

**机制质量增益 = 开启机制的题均分 − 关闭机制的题均分；机制额外消耗 = 开启机制的消耗 − 关闭机制的消耗。** 二值任务的质量增益用成功率百分点表达，负向指标明确反转判断方向。沿用配对差值、区间和最小有意义差异的判断，同时从可观察的工具动作、保留的信息与评分检查项解释改善或退化发生在哪里。

只有单因素对照支持可重复改善，才写“该机制在这些任务上有收益”。跨 Harness 的成绩差、A/B/C 整配置差和轨迹中的相关现象，只能作为机制解释的线索；多项机制同时启用时，只报告组合收益。某机制确实有效，也不能直接推断它解释了两个 Harness 之间的全部差距。

#### 1.6.4 结论三：这些收益需要付出多少任务消耗

对同一组任务，把官方质量与执行消耗关联到每次尝试。主模型、上下文摘要和子 Agent 调用均计入 Harness 消耗；模拟用户、评分器与环境准备费用单列为评测开销。

| 消耗指标 | 计算口径 | 能回答的问题 |
| --- | --- | --- |
| 单次任务消耗 | 统计全部尝试的模型/工具调用、分类型 token 和任务执行墙钟耗时，报告均值及分布 | 完成一次尝试通常需要多少资源，是否存在明显长尾 |
| 每次成功对应的成本 | 同一统计范围内全部已尝试任务的 Harness 执行成本（含失败）/ 官方成功次数；同时披露未评分与用量缺失情况 | 获得一次成功实际需要承担多少尝试成本，而非只看成功样本有多便宜 |
| 机制收益与额外消耗 | 在相同任务上并列报告质量差、调用/token 差、耗时差及可信的成本差 | 某机制的改善带来了多少额外消耗 |
| 质量与预算关系 | 在预先固定的多个预算档位重复比较，绘制各候选的质量—预算曲线 | 同预算谁更好；达到预定质量目标谁需要更少资源 |

只有用量完整、计价规则已核实时才给出货币成本；否则保留可观测用量或下界，货币成本标为 N/A。官方成功次数为 0 时，每次成功成本标为不可计算；未知用量不能按 0 处理。耗时比较使用相同任务与执行条件，不挑各自成功的不同题，也不把并行调用耗时相加当作任务墙钟时间。

“更划算”需要质量与消耗共同支持：在预先约定的质量容差内，质量不退化且消耗下降，或在相同预算下质量提高，才可作相应判断；若质量提高但消耗也增加，报告取舍，不强行排出单一冠军。

#### 1.6.5 最终交付如何对应三个结论

| 目标结论 | 必须交付的结果 | 结论的边界 |
| --- | --- | --- |
| 哪种 Harness 在哪些能力维度更强 | 三候选能力矩阵、逐题官方成绩、配对差值与区间、难度分层和覆盖缺口 | 限定任务范围、版本、配置和预算，证据不足时不排名 |
| 差异与哪些机制有关 | 单机制开/关实验表、质量与消耗增量、机制触发及失败点证据 | 区分已验证机制收益、组合效果和待验证假设 |
| 这些收益需要多少任务消耗 | 调用/token/耗时分布、包含失败的每次成功成本、质量—预算曲线 | 披露用量缺失与计价前提，明确收益和代价的取舍 |

上述结果构成第一部分的能力报告，平台恢复、隔离、容量和维护指标不计入能力分。这里定义评分与结论规则，具体采集、适配、离线统计及当前待开发项由第二篇第 7 节展开。

### 1.7 能力评测的大致路径

| 阶段 | 重点 | 阶段成果 |
| --- | --- | --- |
| 固定能力维度与比较条件 | 明确候选、机制、任务难度、模型、工具、基准版本和预算 | 能力矩阵、任务清单和公平性约定 |
| 建立核心能力基线 | 复用 AppWorld/τ，补齐 GAIA、终端、MCP 和指令判断任务 | 规划、工具、纠错及约束遵循的效果画像 |
| 完成机制对照与难度分层 | 长历史、Skills、协作等有/无配对，观察长链路和高难度任务 | 单项机制增益、性能退化趋势和任务消耗 |
| 形成能力结论与回归集 | 比较有意义的效果差异，保留逐题轨迹及评分证据 | 能力排序、失效分析、证据局限和效果回归集 |

先跑通少量任务及评分链路，再冻结正式实验；发现失败模式后补充诊断实验，并用独立任务复核。具体运行和评分步骤由[第二篇](harness-selection-evaluation-implementation.md)展开。

## 第二部分：Managed Agents 平台本身的要求

### 2.1 目标、对象与边界

Managed Agents 不仅需要“回答正确”，还要承载**可持续、多租户、有副作用的执行过程**。本部分评价的是 Gateway、Control Plane、Agent Service、Agent Harness Runtime、Tool Worker 及其存储、消息和外部工具依赖组成的服务链路，验证其在各候选 Harness 配置下是否满足托管要求。

这里需要回答：进程失败后能否继续；请求重复或执行结果未知时能否避免错误副作用；租户和 Session 是否隔离；取消、预算、用量和输出是否具有可信语义；并发负载下是否可运营、可维护。缺陷应归到共享平台、Harness 适配层、内核或外部依赖，不能把所有服务问题都记成 Harness 推理能力不足。

当前 Codex 直接链接固定版本 `codex-core`，不是 CLI/app-server，也不经过 Node 宿主。一次部署选择一种内核；Session 绑定该内核和原生状态格式。本轮验证同内核跨进程、跨副本恢复，不要求把一个执行中的 AgentScope Session 迁到 Codex。依据[当前协议实现映射](../agent-harness-runtime/protocol/implementation-map.md)。Pi Durable 需以独立镜像、状态格式和结果完成相同平台验收，不能沿用普通 Pi 的结论。

当前三种候选已具备共同 Session 入口的接入基础，这是本轮实施范围的工程前提。ADK、DeepAgents 等尚无同等适配和验收证据，后续若新增，应单独完成接入与准入，不把集成成熟度当作第一部分的能力优势。Pi Durable 的持久化差异在本部分验证；只有推理或执行策略同时变化时，才追加能力对照。

### 2.2 需要覆盖的平台要求与场景

| 平台要求 | 需要覆盖的场景 | 验收证据与判断重点 |
| --- | --- | --- |
| 持久状态与持续执行 | 挂起/恢复、进程重启、副本接管、长工具等待、状态提交中断 | 已确认状态不丢失，恢复后的执行与提交状态一致；未知结果有明确处置 |
| 副作用与重复处理 | 重复请求/消息、工具已执行但响应丢失、写入期间接管 | 幂等或去重依据可核验；未知写入不被盲目重放，最终业务状态与操作记录一致 |
| Session、Turn 和取消语义 | 并发消息、排队、断流、重新读取输出、取消与工具完成竞态 | 接收、运行、终结和输出状态一致；断流不被当作取消，取消后残余执行收敛 |
| 多租户与资源隔离 | 跨租户/Session 访问、凭证与工作区隔离、数据和状态串用 | 未授权访问被拒绝；数据、工具权限及凭证不跨边界泄露 |
| 权限与人工确认 | Agent 发出越权调用、未确认写操作、确认失效或撤销 | 授权由服务端强制执行，不依赖 Harness 自觉遵守；拒绝及确认过程可审计 |
| 预算与用量 | 长任务、辅助模型/子 Agent 调用、失败和取消、用量缺失 | 限额按定义生效；用量完整、可对账，异常明确暴露，不把缺失记成零 |
| 容量与资源治理 | 长短任务混合、多租户并发、排队、限流与下游变慢 | 吞吐、尾延迟、饱和点和资源占用可测；避免持续饥饿并明确背压/降级行为 |
| 可观测、运维与升级 | 跨组件故障定位、上游升级、状态兼容、回滚与新内核接入 | 可串联 Session/Turn/工具证据，定位故障来源；升级与维护成本可接受 |

同一个业务任务可以提供两组证据，但判据必须分开。例如，AppWorld 任务的业务目标是否完成属于第一部分；在写工具执行期间杀掉进程后，操作是否重复、状态是否一致属于本部分。AgentDojo 的行为表现也不能代替租户隔离和服务端权限测试。

### 2.3 评测方法与框架选择

通过 ACS 与 Session API 开展能力实验前，先完成最小运行基线，确认输入、工具结果、预算和输出链路可信。运行环境异常按责任层单独归因；能力评分只反映其规定实验条件下能够解释的结果。

本部分采用**平台专项 D 赛道**：先用确定性模型和工具夹具隔离推理随机性，验证状态与协议，再用真实模型、代表性业务任务确认完整链路。固定发布版本、资源规格和基础依赖，分别改变故障位置、负载、重启和网络条件；普通无故障运行作为对照。

| 方法/组件 | 选择依据 | 能证明什么 |
| --- | --- | --- |
| 现有平台验收与故障回归工具 | 直接覆盖本项目 Session、预算、租约、取消及组件边界 | 在可重复故障条件下验证服务语义和恢复行为 |
| 现有 `general-agent-eval` Runner 与审计记录 | 与能力实验走相同 Session 入口，可复用证据关联 | 验证真实业务执行与状态、用量、工具审计是否一致 |
| ACS 负载与资源观测 | 部署环境中的调度、存储、网络和配额共同决定容量 | 给出各配置在明确负载下的吞吐、延迟和资源边界 |

公开 Agent 数据集不覆盖本项目的分布式协议和租户模型，因此本部分以自有协议契约、故障矩阵和验收用例为主，不再另选一个通用能力榜单作为平台合格证明。Harbor 或 Inspect AI 可以提供任务负载与评分复用，但不替代这些平台验收。

对三种候选运行同一套准入矩阵。共享链路故障与候选特有适配故障分开归因；已通过的基础验收可作为起点，发布或适配发生变化后需重验。已有验收不代表完整故障与容量范围均已覆盖。

### 2.4 如何形成平台验收结论

本部分单独输出验收矩阵、故障证据、容量边界及维护评估，不生成“解决问题能力分”。

| 结论类别 | 判据与用途 |
| --- | --- |
| 必须满足的正确性门禁 | 权限隔离、已确认状态持久性、重复副作用、取消及预算等关键语义按约定通过；任何未解决的关键问题阻止最终准入 |
| 可运营条件 | 给出适用负载、资源配置、用量可核验程度和告警/排障能力；条件不完整时明确部署限制 |
| 工程选择依据 | 记录适配改动范围、上游升级/回滚难度、状态兼容和团队维护成本，支持能力接近时的取舍 |

平台侧的尾延迟和吞吐需在可比并发与资源条件下测量；第一部分的单任务耗时不能替代容量结论。平台侧负责证明用量记录可信，第一部分据此比较完成任务所需的消耗，避免将“计量完整”误认为“推理高效”。

准入通过、待修复和未覆盖项逐项列出，并标明受影响的候选与责任层。修复后以新批次验证，保留原始失败；具体阈值、测量方式和证据格式由[实施方案](harness-selection-evaluation-implementation.md)承接。

### 2.5 平台验证的大致路径

| 阶段 | 重点 | 阶段成果 |
| --- | --- | --- |
| 建立最小可信基线 | 冻结部署与适配版本，确认基本 Session、工具、预算和评分链路 | 可开始正式能力实验的配置，以及必须先修的问题 |
| 完成正确性专项 | 状态恢复、副作用、隔离、权限、取消与用量故障矩阵 | 分候选准入结论和缺陷归因 |
| 验证容量与维护 | 多租户混合负载、资源观测、升级/回滚及排障演练 | 可运营范围、资源成本和长期维护证据 |
| 形成平台报告与回归集 | 固化验收证据、未决项和重复验证入口 | 平台准入报告、故障回归集和发布检查要求 |

在现有三种内核接入基础上，以评测和平台工程师各一名、兼职基础设施与业务评审为假设，两部分合计首轮按约 4–6 周规划，部分工作并行；新增内核、GUI 环境或重大缺陷另估工期，完整范围以阶段出口为准。

### 2.6 两部分如何共同支持最终选型

最终报告并列呈现**能力结论**与**平台准入结论**。Managed Agents 的目标业务、产品承诺和部署约束在此用于映射与取舍：引用第一部分已经得到的能力证据，判断哪些候选适合实际使用场景；不据此扩大第一部分的评测目标或修改其能力权重。先看平台是否达到必要门槛，再在合格候选之间比较任务效果、任务消耗及维护代价。

| 第一部分的能力结论 | 第二部分的平台结论 | 选型处理 |
| --- | --- | --- |
| 主要场景效果更好 | 必要门禁通过，运营条件明确 | 可作为默认或相应场景候选，结合成本与迁移代价决定 |
| 主要场景效果更好 | 存在未解决的关键平台缺陷 | 保留能力优势证据，修复并重验后再决定上线准入 |
| 无明显效果优势 | 平台成熟、运营与维护成本可接受 | 可保留现有基线，或用于有明确收益的特定场景 |
| 关键能力或平台证据不足 | 未覆盖或结论不确定 | 补齐证据，不宣布全面胜出或可用 |

替换基线不是唯一成功结果。统一默认、按场景为新 Session 选择内核，以及证据不足时继续保留基线，都是有效结论。最终交付两组报告与回归证据，实施步骤由[第二篇](harness-selection-evaluation-implementation.md)展开。

数据集与框架依据见第一部分中的官方链接；项目事实参考[已有 Harness 选型研究](../../docs/brain-harness-selection-research.md)、[杭州一致性验收](../tests/general-agent-eval/reports/hangzhou-consistency-20261101.md)和[业务批次记录](../tests/general-agent-eval/reports/formal-business-20261101-182203/README.md)。工程预评估、任务效果实测和平台验收应分别引用，不能互相替代。
