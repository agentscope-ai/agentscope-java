# 传输选型：协议推送 vs 存储解耦

> 状态：待决策
> 问题域：**怎么传**——数据面与控制面之间用协议还是用共享存储
> 关联文档：[sdk-design.md](./sdk-design.md)、[session-storage-topology.md](./session-storage-topology.md)、[session-transcript-append.md](./session-transcript-append.md)

---

## 1. 现状与疑问

[sdk-design.md](./sdk-design.md) 定义了四层上报设计与 ASDP / HTTP 的混合通道：ASDP gRPC 负责上行推送，内嵌 HTTP 负责下行拉取与命令。

两个疑问推动了本次重新评估：

1. 对 session event 这种流式、体量大的数据，为什么用 HTTP 轮询而不是已有的 ASDP 推送？
2. 是否应该由数据面直接写入某种存储，两侧通过存储解耦？

---

## 2. 为什么 Managed 场景没走 ASDP 推送

### 2.1 ASDP 被 K8s 硬门控

`cmd/aistiod/main.go` 中，ASDP gRPC server 的启动挂在 Kubernetes 连接之下——不连 K8s 就不启动。Managed 形态以独立进程运行，因此这条通道在该形态下**根本没开**。

Java 侧对应地，`AistioConfig` 也建议独立部署时保持 `startGrpc=false`。

### 2.2 真实原因是路径依赖，不是「普适性」

早前的论证里有一条「HTTP 更普适，第三方框架不一定能实现 gRPC」。这条站不住：我们适配 ADK 之类的第三方框架本来就走 wrapper / instrument 模式，wrapper 自己实现 gRPC 客户端没有障碍。

更诚实的原因是：

- **历史与兼容**：poller + HTTP 合约先落地，session 相关能力顺着既有路径长出来。
- **回避多副本命令转发**：下行命令要求「找到持有该连接的副本」，多副本下需要跨副本转发或 leader 聚合。[storage-followups.md §4](./storage-followups.md) 已把这件事单列为待设计项。用 HTTP 拉取可以绕开它。

所以四层设计**不是错的，是被普遍化了**——它是跨信任域场景的正确答案，被原样套用到了共享数据库/共享基础设施的场景上。

---

## 3. 切分线是信任域，不是 Managed / BYO

### 3.1 同信任域：存储解耦更合适

Managed 托管、客户私有化部署，数据面与控制面在同一信任域内，甚至共享同一个 Postgres 实例。此时引入一层传输协议只是在同一台机器内部搬运数据，代价包括序列化、第二份存储、复制延迟、两侧保留策略漂移。

**真正的选择不是「协议 vs 无契约」，而是「契约用 protobuf 表达，还是用存储布局 / SQL 视图表达」。** 后者在共享基础设施下每个维度都更便宜，且视图同样具备所有权与版本演进能力。

### 3.2 跨信任域：取决于存储的授权粒度

早前结论是「跨信任域必须走协议」，理由是不能给第三方发数据库凭据、开网络、共享表结构。**这个结论需要修正。**

关键变量是存储的授权粒度：

| 存储 | 授权粒度 | 跨信任域直写是否成立 |
|------|---------|---------------------|
| 关系数据库 | 库 / 表 / 行（行级需 RLS + 每租户角色） | 不成立，运维复杂度过高 |
| 对象存储 | **前缀级 IAM + STS 临时凭据** | **成立** |

可以给第三方 wrapper 发一个短期有效、只能写 `bucket/tenant/{tid}/session/{sid}/*` 前缀的 STS 凭据。这比数据库凭据模型好得多，也比维护一个协议端点简单。

因此修正后的结论是：**跨信任域走协议还是走存储，取决于存储的授权粒度；对象存储的前缀级授权足够，直写成立。**

### 3.3 决策矩阵

| 场景 | 上行（事件 / transcript） | 下行（命令） |
|------|--------------------------|-------------|
| Managed 托管 | 直写共享存储 / 读视图 | HTTP 或 ASDP，见 §4 |
| 客户私有化部署 | 直写共享存储 | 同上 |
| SaaS 接第三方 agent | 对象存储 + STS 前缀凭据 | 协议（命令必须实时且需寻址） |

注意上行与下行的需求本质不同：上行是「大量数据的单向流动」，适合存储；下行是「低频、要求实时、需要寻址到具体实例」，适合协议。当前设计把两者绑在同一套通道假设上，是混淆的来源。

## 4. ASDP 的定位

ASDP 不应被废弃，但定位需要收敛：

- **保留**：跨信任域 BYO 的上报通道；下行 `SessionCommand`（`asdp.Distributor.SendSessionCommand` 早已存在但从未接线，见 [storage-followups.md §4](./storage-followups.md)）。
- **不再承担**：Managed 场景的 session event 复制。该场景改走存储解耦。
- **待解**：K8s 硬门控是否解除。若要在非 K8s 形态使用 ASDP 下行命令，这个门控必须处理。

---

## 5. 第三方 wrapper 的存储契约

若采用对象存储直写，需要文档化以下内容作为对外契约（替代原本由 protobuf 承担的角色）：

1. **JSONL 行 schema**：事件类型枚举、必填字段、扩展字段约定、版本标识。
2. **前缀布局**：`{tenant}/{agentId}/{sessionId}/events/{seqStart}-{seqEnd}-{writerId}.jsonl`，与 [session-transcript-append.md](./session-transcript-append.md) 一致。
3. **授权模型**：STS 凭据的获取方式、作用域、有效期、续期。
4. **写入约定**：分段不可变、`writerId` 唯一性、seq 单调性、flush 时机与尾部持久性预期。
5. **索引回写**：wrapper 是否需要同步上报计数与 token 聚合，还是由控制面从对象异步派生。

第 5 点需要决策——异步派生实现简单但有延迟，同步上报实时但把索引写入也变成了对外契约的一部分。
