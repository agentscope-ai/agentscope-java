# Managed Agents 效果评测一致性改造计划

制定日期：2026-10-31。适用对象：杭州集群的 AgentScope、pi、codex 三套 Managed Agents。

本文保留依据 2026-10-30 代码审查、部署核对和首题验收制定的原始差异与目标。2026-11-01 已完成可实施改造并部署到杭州，当前状态见[实施与验收记录](consistency-implementation.md)；早期模型统一结果保留在[原验收记录](reports/hangzhou-qwen38-20261030.md)。每轮评测仍需重新预检集群。

## 目标与排序原则

目标是在相同任务、模型和外部预算下比较 Harness 的任务完成能力。统一评测输入、可用能力和资源边界，保留 Harness 的规划、上下文管理和恢复实现，并把这些实现差异记录下来。

优先级按对成功率、最终业务状态和结果可比性的影响划分，不按开发难度排序。P0 是扩大正式评测前的必做项；P1 是长任务或多轮效果评测前的必做项；P2 是扩大并发及比较性能、成本前的必做项。同级建议按表内顺序实施。已有首题结果作为链路验收保留，不作为整体能力排名。

| **P0-1 实际模型请求参数** | 公共 model profile 已统一模型、协议、temperature、reasoning 和输出预算，但 `top_p`、`tool_choice`、`parallel_tool_calls` 等未全部显式规定；SDK 还会补充字段。Java 从 profile 读取 180 秒超时，pi 和 Rust 当前分别在代码中默认/固定为 180 秒。 | 配置文件相同仍可能发送不同请求；后续改一个配置可能只对部分实现生效。 | 在公共契约中规定可控字段的值或“必须省略”规则；三套适配器读取同一请求时限。增加脱敏请求审计，检查实际出站字段；不要盲目补齐供应商不支持的参数。落点：model profile、封存配置、模型适配器。 | 同一工具往返样例的出站参数与模型标识符合契约；差异有显式允许清单。修改公共超时后，三者实际截止时间同步变化。 |
| **P0-2 Case 总预算与停止条件** | Java 的 `maxIters` 是迭代上限，pi/codex 被映射为模型调用上限；Java 可能有额外收尾调用。τ-bench 当前每 Turn 300 秒，最多 30 次用户交互，不能代表整个 case 只有 300 秒；AppWorld 当前单 Turn 900 秒。 | 同一个数值给三者的推理机会不同；多 Turn 或恢复可能获得更多计算机会。 | 新增每个数据集的统一 case 预算：总时间、模型请求次数、累计输入/输出 token、业务动作数。平台持久化计数覆盖全部 Turn 和恢复；压缩、收尾、失败请求纳入相应计数。保留原生迭代限制作为内部保护，不能替代共同预算。落点：Session 预算账本、Runner、适配器。 | 在多 Turn、Pod 重启及压缩测试中预算不重置；边界相同；超限归为 `budget_exceeded`。τ-bench 官方 30 动作约束单独保留，不能等同 30 次模型调用。 |
| **P0-3 重试与恢复预算** | 请求 SDK 层已做限制，但 pi 原生 Agent 默认仍开启最多 3 次重试；其 Worker 的 `retryBudget=8` 耗尽后采用更长退避，并非永久终止。codex 和 Java 恢复路径也不同。 | 某一实现可能通过更多尝试提高成功率，或长期恢复直至耗尽 Runner 时限。 | 明确 HTTP 请求、原生 Agent、Worker/Session 三层语义。基础对齐模式关闭额外原生重试；原生效果模式保留恢复策略，但共享持久化恢复次数和总时间上限。记录触发原因、退避和每次真实模型请求。落点：Session Service、运行时重试配置、Runner。 | 注入一次 429、断流和 Worker 重启后，账本能解释全部尝试；无无限恢复；恢复不能重置 P0-2 预算。未知外部副作用不能盲目重做。 |
| **P0-4 工具并行、顺序与副作用** | Java 显式允许模型一次返回多个工具调用，pi 工具执行设置为串行，codex 支持待执行调用批次。这是不同层面的设置，不能直接当作同一个并发参数。AgentScope AppWorld 首题存在重复发送，尚未归因。 | 有状态写操作的顺序和重复执行会直接改变官方评分所检查的数据库。 | 分开配置“允许多工具响应”和“同一 case 的工具执行并发”。基础对齐模式先逐个调用、按稳定顺序执行；原生模式可保留多调用，但写操作排序规则一致。同一调用身份恢复时复用已接受结果；模型主动发起的新调用不能被静默去重。落点：模型适配器、Tool Worker、结果账本。 | 记录模型调用 ID、工具调用 ID、参数哈希和结果 ID；恢复同一调用不重复产生副作用。能区分模型重复决策与执行重放。不得以更改评分或覆盖失败结果代替修复。 |
| **P0-5 有效提示词、工具集合与权限** | Runner 提交的业务 system 相同，但各 Harness 会加工提示词及工具表示；codex 使用 `hands_` 工具名前缀。评测已禁用通用内置工具，但最终模型可见内容还需核对。 | 额外提示、工具、知识或更宽权限会改变任务难度。 | 封存任务提示词、官方政策、工具 schema/描述、权限和初始输入；核对最终出站请求。关闭未声明的 shell、网络搜索、技能和跨 case 记忆。允许协议所需名称映射，保留可逆映射表；原生模式保留必要 Harness 指令并单独记录。落点：Agent 定义、封存工具目录、适配器。 | 三者有相同业务能力和权限；工具名称映射可逆；最终提示词和工具集有哈希及允许差异说明；无本机或工作区隐式配置注入。 |
| **P0-6 环境重置、评分与失败分类** | 当前新 Session、数据集版本和官方评分路径已具备；仍依赖共享可变环境槽位、Runner 协调及人工恢复。首题中 codex 曾从未重置的环境恢复评分。 | 脏数据、遗留执行或把基础设施失败当能力失败，会污染成功率。 | 每个 case 持有独占槽位租约；确认旧执行终止后重置并校验初始状态。评分完成并导出后释放槽位。区分官方得分失败、预算耗尽、基础设施错误和未知状态；后者停止复用环境。预先规定重跑规则，保留所有尝试，不能择优覆盖。落点：Runner、环境控制器、结果格式。 | 并发 Runner 不会重用同一槽位；异常退出可恢复；初始状态和最终官方评分可追溯；同时报告端到端成功率、基础设施错误率和有效评分样本数。 |
| **P1-1 上下文压缩与历史裁剪** | Java 默认保留压缩及工具结果裁剪，压缩预留约 20,000 token；pi 默认启用压缩，预留 16,384、保留近期 20,000 token；codex 当前适配尚未完整集成自动压缩路径。相同 262144 上下文窗口不等于相同实际历史。 | 长任务可能因历史丢失、摘要失真或上下文超限失败。 | 基础对齐模式使用不触发压缩的短任务；支持显式关闭时统一关闭，触发阈值的样本标为超出该模式范围。原生效果模式保留各自压缩策略，记录触发、保留量、摘要请求和裁剪量，并计入公共预算；codex 缺失能力单独标注或补齐接入。落点：上下文配置、各适配器、轨迹。 | 短任务基线没有隐式压缩；长任务能还原压缩前后历史变化；辅助模型调用纳入预算。不得宣称三者长上下文能力已经对齐。 |

| **P1-3 模拟用户、采样与运行顺序** | τ-bench 模拟用户已统一为 qwen-plus，但随机参数与版本记录需要完善；测试目前按 Harness 分组运行，目标和模拟用户模型别名都可能变化。 | 模拟用户配合程度、随机波动及供应商时段变化会混入 Harness 差异。 | 封存模拟用户提示词、参数和可用版本信息；供应商支持时记录 seed，不承诺完全确定性。按 task/repeat 交错三者运行并平衡先后顺序；先用少量重复试运行估计成本，再冻结正式重复次数。落点：Runner、manifest。 | 每条结果关联任务、重复号、模型信息、模拟用户配置和运行时段；重复次数一致；不把固定用户对话回放误当正常交互评测。 |
| **P2-1 部署资源、并发与排队** | 核对时 Java Harness 为 4×8 CPU/16 GiB，pi/codex 为 2×4 CPU/8 GiB；Tool Worker 并发 1024 对 64，事件投影并发 64 对 8；Agent Service 单 Pod 资源也不同。 | 主要影响时延和吞吐；存在超时预算时也会改变成功率。 | 质量基线先限制每个目标同时运行的 case 数，保证无资源竞争；性能赛道再统一副本、资源、并发和后台负载。分别记录排队、模型、工具和投影耗时。case 时限起点统一，不能按目标改变。落点：Helm evaluation overlay、调度器、指标。 | 质量基线无持续 CPU 限流/OOM/异常积压；性能报告列明等额资源及负载；不能用现有首题耗时作公平性能排名。 |
| **P2-2 统计口径与发布审计** | 已有模型 profile 和镜像摘要，但公共 evaluation profile、每轮自动预检和完整预算/恢复统计尚未形成闭环。 | 配置漂移会让回归结论失真；cost 占位为零不能用于费用比较。 | 增加 evaluation profile；每轮封存模型/profile 哈希、代码/依赖版本、镜像摘要、有效定义和资源快照。输出成功率、错误率、预算耗尽率、模型/工具请求、token、恢复次数及延迟。费用使用真实计价依据，缓存 token 单独记录。落点：配置、CI、Runner、报告。 | 运行前遇到未允许的差异直接停止；结果可关联全部配置；未取得真实价格时仅报用量，不报零成本；新旧批次不混算。 |

## 实施方式与边界

新增公共 `evaluation profile`，与现有 [model profile](../../deploy/profiles/qwen38-eval.json) 分开：前者描述数据集、case 预算、工具策略、恢复上限、重复采样和部署约束，后者描述模型请求。字段名称和数值在实现时确定，本文不把建议字段冒充当前已支持的 API。

预算范围必须明确为 case、Session 或 Turn。一个 case 涉及多 Turn 时共用 case 预算；未来存在子 Session 时也归入同一 case。模型请求尝试数在发出前登记，token 用量在响应后结算；断流导致用量未知时保留未知标记并采用预先定义的保守预算处理，不能记成零消耗。总时间从统一的 Runner admission 起点计时，排队时间单独展示。

按职责实施：Runner 负责案例生命周期、评测编排和评分；Agent Service / Session Service 负责持久化准入与公共预算；Harness Runtime 负责参数映射和原生行为；Tool Worker 负责工具执行与副作用结果交接。不能在 Runner 中重新实现三套 Agent 推理循环。

建议分三批交付：

1. **共同评测条件**：完成 P0，增加实际请求对照与故障注入验收；三者重跑相同少量短任务，使用新批次标识保留旧结果。
2. **长任务与原生能力**：完成 P1，明确基础对齐和原生效果两种模式；增加长历史、长工具返回和多轮任务，冻结正式任务清单与重复次数。
3. **规模与回归**：完成 P2，统一性能赛道资源，接入自动预检和回归报告。P2 的配置快照与用量记录可从第一批提前建设。

本计划不要求更换三套 Harness 的原生规划算法或强制使用同一摘要实现。若为基础对齐临时关闭某项能力，报告必须标明；原生能力缺失则如实记录，不能通过增加未声明的外部能力掩盖。
