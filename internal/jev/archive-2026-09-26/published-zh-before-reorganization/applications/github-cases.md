## 1. JEV技术与应用场景调研

| GitHub项目 | 来源中的具体实践 | 可借鉴点与证据边界 |
| --- | --- | --- |
| [spring-ai-typesafe](https://github.com/spring-ai-community/spring-ai-typesafe) | Judge、有限自我修订、输入输出护栏、文档过滤与重排、工具索引 | 原子问题由代码组合；可作为组件设计主参考。存在集成与示例，不等于已证明业务收益 |
| [jevals](https://github.com/openlayer-ai/jevals) | 对轨迹判断工具选择、是否使用工具结果、事实依据、完整性及注入风险 | 复用评估定义，批量提出多维问题；后端支持与性能数字是项目声明，需本地验证 |
| [Foreman](https://github.com/thruwire/foreman) | 独立观察编码worker的进度、偏航、验证需求和完成证据 | 判断与动作仲裁分离、观察去抖、有限纠偏；项目明确定位为架构实验，不能当作成熟多Agent调度系统 |
| [fast-jev-compaction](https://github.com/tamaratran/fast-jev-compaction) | 对工具调用及结果做保留、截断、移除，维护配对 | 借鉴选择性保留原文和最近消息保护；这是上下文压缩，长期记忆准入是我们的扩展规划 |
| [Jevonian](https://github.com/xinyao27/jevonian) | 先按协议、配额和上下文等约束筛选，再让JEV选择模型与推理深度，记录用量 | 候选约束优先、阶段路由和成本账本；不直接迁入其代理服务，也不引用未复现节省率 |
| [jev-review](https://github.com/devagrawal09/jev-review) | 风险筛查、文件画像、证据选择、机制分类、严重度及审查路由 | 用有限判断缩小审查范围；结果是待核查线索，不能替代测试或作为自动合并依据 |
| [jev-ultrafast](https://github.com/browser-use/jev-ultrafast) | 从当前页面生成编号元素，选择操作与兼容目标，必要时由文本模型填写文字 | 将动作选择与文本生成拆分；演示速度不能外推为复杂浏览器任务成功率 |

补充资源：[JevBench Hard](https://github.com/fstandhartinger/jevbench/blob/2fa63fa3226cb369795525ed011800f57dcbd894/datasets/HARD-TIER.md)用于复杂判定回归，并非应用案例。已有111题对照详见[本项目评测](/v2/zh/jev/evaluation)；该结果不支持默认假设JEV在所有任务上准确率或尾延迟都优于文本模型。替代后端属于独立兼容性验证，不作为首期应用集成前提。

## 2. 与AgentScope Service及Harness结合思路

此前讨论的AgentCore在本项目统一映射到AgentScope Service。Service负责承接配置、运行关联、决策记录及评测入口的集成；Harness负责执行边界；应用层负责业务语义和确定性规则。下表是我们的设计推导，不是外部仓库已经实现的AgentScope功能。

| 工作项/优先级 | AgentScope落点 | 最小应用流程 | 验收重点 |
| --- | --- | --- | --- |
| JEV-01 / P0：统一评估 | JevClient及离线runner；Service关联run/session和版本 | 已完成轨迹→原子判题→人工金标对照→按用途报告；后续同一定义进入在线影子评估 | 缺字段、非法结构、超时均可区分；离线与在线定义一致 |
| JEV-02 / P1：客服Judge | 应用服务、拟议Judge组件；Service保存草稿与判定记录 | 工单→诉求/条件提取→路由建议；回复草稿→承诺与完整性检查→有限修订 | 条件性退款、多个诉求、证据不足；金额与退款执行仍由业务规则控制 |
| JEV-03 / P1：工具与护栏 | 现有ToolSelection/Auto中间件，新增内容检查边界 | 已授权候选→适用性筛选→工具计划→执行前复核；输出先审核再发布 | none不恢复全量工具；ERROR不等于拒绝；工具只执行一次；流式审核明确缓冲边界 |
| JEV-04 / P1：知识助手 | 应用检索后处理，复用Judge | ACL过滤→相关性筛选→重排→回答→引用支持检查 | 无证据弃权、冲突证据、排序质量、最终答案正确率及总延迟 |
| JEV-05 / P2：研发监督 | Harness事件观察、Team适配；Service展示证据与建议 | 有界轨迹/差异/测试结果→进展与风险判断→规则选择继续、请求验证或人工处理 | 测试未执行不能认定通过；先旁路报告，后验证幂等干预、状态版本与冷却期 |
| JEV-06 / P2：上下文治理 | Compaction及独立Memory写入策略；Service记录恢复引用 | 保护近期与关键约束→调用/结果成对评分→保留或卸载→需要时恢复 | 关键事实保留、配对完整、任务成功率；记忆写入另测冲突与用户隔离 |
| JEV-07 / P2：模型路由 | 现有ModelRouter增强；Service模型资源及用量记录 | 能力/权限/健康筛选→阶段判断→选模型→阶段内粘性→对照质量与用量 | 路由开销、缓存损失、故障回退、总成本；不只比较单次模型价格 |
| JEV-08 / P3：浏览器任务 | 应用浏览器工具适配；Service保存页面版本与动作轨迹 | 页面可见候选→选动作/目标→执行前重校验→观察→完成验证 | 页面变化、过期索引、BLOCKED/DONE区分；先查信息，不自动提交订单 |

业务覆盖由三条纵向试点展开：客服覆盖分流、Judge和护栏；知识助手覆盖检索与引用；研发助手覆盖监督、审查和交付证据。数据运营中的分类、质量筛查可以复用已验收的Judge，不需要等待完整Harness接入。

公共依赖优先复用现有JevClient、RuntimeContext和Middleware。Service的具体字段与接口实施前对照当前代码确认，不复制外部Advisor或代理协议到核心层。拟议组件和API在实现前始终标为待实施。

## 3. 待验证计划（TBD）

按[实施路线](/v2/zh/jev/implementation-plan)推进，先P0和JEV-02纵向闭环，再扩展工具/RAG；P2先做影子实验，P3浏览器按独立应用验收。

每个场景使用相同输入比较现有流程、JEV增强和Qwen文本判定三个版本。固定数据、模型版本、提示/题目定义、候选集合及运行环境；离线随机交错运行并重复采样，生产影子只记录建议。在线评估不能使用事后才出现的证据，否则与离线结果不可比。

| 验证组 | 数据与失败用例 | 进入执行模式的条件 |
| --- | --- | --- |
| 判定/客服/护栏 | 中文真实脱敏样本、条件反转、注入、无候选、工具多调用 | 分场景准确率、风险漏判及误拦截达到业务约定；阈值在校准集确定，测试集独立 |
| 检索/评审 | 无关片段、冲突版本、无来源断言、缺少测试、真实缺陷与非缺陷变更 | 证据召回、误报、答案或审查质量优于可接受基线 |
| 监督/压缩/路由 | 长任务轨迹、停滞与正常探索、关键旧事实、模型切换及失败 | 任务成功率不退化到约定界限之外，误干预和信息损失可控，有可靠回退 |
| 浏览器 | 固定测试站、动态页面、目标消失、需要文字填写、不可完成目标 | 独立验证任务成功；不能仅凭JEV回答DONE计成功 |

所有组记录准确率/分项召回、结构失败率、弃权率、额外判断耗时及端到端P50/P95、重试、token和实际可核算成本。样本量、重复次数、质量非劣界限、用途阈值、延迟预算、上线比例及负责人均为TBD，由首批基线和业务目标确定，不沿用开源默认概率阈值。

每项研发交付包含固定来源commit、接口与状态约定、离线行为测试、可运行示例、金标数据与报告、Service可追溯记录和回退演练。当前页完成的是规划映射，没有新增生产组件，也没有复现项目宣传指标。
